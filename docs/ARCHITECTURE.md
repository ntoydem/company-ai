# ARCHITECTURE — Architecture Decision Records

Short, numbered decisions with rationale. Not a design narrative. Add a new ADR when a new
architectural decision is taken; supersede (do not silently edit) an ADR when a decision changes.
Status values: `accepted` | `superseded by ADR-xxx`. Phase column = when the decision becomes code.

## ADR-001 — Topology: one VM, one Compose project
**Status:** accepted · **Phase:** 0.1
- One Ubuntu 24.04 VM on Proxmox, one `docker compose` project (`infra/docker-compose.yml`), same file for dev and prod; only `.env` differs.
- Default services: `postgres` (pgvector/pgvector:pg16) and `backend`. `ocr-worker` joins the default set in Phase 0.2.
- Profiles: `web` → `caddy` (Phase 3.3); `full` → `embed` bge-m3 (Phase 3.4). `make up` never starts profiled services.
- Persistent data lives under `DATA_ROOT` as bind mounts (`postgres/ documents/ excel/ app-data/ backups/`); containers are disposable.
- Host exposure: only ports listed in `.env`. Postgres, ocr-worker and embed are reachable solely on the compose network.
- Why: minimal moving parts, restorable from `git clone` + `.env` + `make up`; no Kubernetes, no external queue.

## ADR-002 — Backend layering and data access
**Status:** accepted · **Phase:** 0.1
- Python 3.12, FastAPI, Pydantic v2. Layers: `app/api` (HTTP only) → `app/services` (rules) → `app/repositories` (queries) → `app/models` (ORM). Schemas in `app/schemas`.
- **Synchronous** SQLAlchemy 2.x with psycopg 3. Rationale: simpler code and tests, Alembic and DuckDB are sync, request volume is LAN-scale; FastAPI runs sync endpoints in a threadpool.
- One Alembic migration chain (`backend/alembic/versions`), applied by the container entrypoint at startup (`alembic upgrade head`).
- Settings via `pydantic-settings` from environment variables only; no config files in code.
- Dependencies pinned with `uv.lock`; everything (tests, lint) runs inside the backend image, the host needs only Docker + make.

## ADR-003 — Authentication
**Status:** accepted · **Phase:** 0.1 (users table, admin seed) · 1.1 (login endpoints)
- JWT in an httpOnly + SameSite cookie, 8-hour lifetime, no refresh token; logout = cookie clear.
- Passwords hashed with Argon2id (`argon2-cffi`); plaintext never stored or logged.
- `users` carries `auth_provider` (`local` only in V0) and `external_id` so SSO/Entra ID can be added later without schema change. No SSO in V0.
- Initial admin is created idempotently at startup from `ADMIN_USERNAME` / `ADMIN_PASSWORD`; an existing user is never modified by the seed.
- Login rate limiting (Phase 1.1) protects the single password endpoint.
- **Phase 1.1 concretization:** JWT via `PyJWT` (HS256, `JWT_SECRET`), cookie name `access_token` (`path=/`, `samesite=lax`, `secure=false` in V0 plain-HTTP LAN, ADR-015). The token's `sub` (user id) and `role` claim are non-authoritative — `get_current_user` re-fetches the `User` row on every request and trusts only the DB's `role`/`is_active`, since there is no refresh/revocation mechanism. Wrong username, wrong password and a disabled account return an identical 401 (no username enumeration). Login rate limit: in-memory, 5 failed attempts/15 min per username and 20/15 min per client IP (no Redis in this stack; single `uvicorn` process makes this sufficient for V0; resets on restart). Demo users `yonetim`/`finans`/`hukuk`/`enerji` are seeded the same idempotent way as admin, sharing one `DEMO_USER_PASSWORD` — they carry only a `role` until Phase 1.2 adds department membership.
- **Phase 3.3 concretization:** the UI never reads the JWT (httpOnly); its only notion of "logged in" is `GET /api/auth/me` (200 → user, 401 → login screen), and any later 401 drops the session client-side. `/me` (and `/login`) now also return `department_slugs` — the user's direct memberships — so the home screen can hide cards of departments the employee cannot see; this is convenience only, ADR-004's server-side gate is unchanged.
- **Aşama A concretization (30.09.2026):** `/me` and `/login` also carry `enabled_products` (ADR-022); `CurrentUserResponse.from_user()` composes user attributes with the company-wide row instead of `model_validate(user)`.
- **Aşama C (01.10.2026, B-09/B-05):** `users.primary_department_id` (FK, SET NULL; must be one of the memberships, NULL for management/admin; backfilled from the earliest membership, ties by slug) and `users.title`. `/me`/`/login` return `primary_department_slug` and `title`, and `department_slugs` lists the primary first — so the AI-BalBal build that reads `department_slugs[0]` as the home department is correct without a change. `GET /api/directory?q=&department=` is the everyone-can-read people list (five fields, active users only, membership-based department filter); `/api/users` stays admin-only. `manager_id` was deliberately not added (B-22).

## ADR-004 — Authorization model and the `allowed_document_ids` contract
**Status:** accepted · **Phase:** 0.1 (contract) · 1.2 (rules)
- Exactly one gate: `app/services/authorization.py::allowed_document_ids(user, scope, document_ids_provider) -> set[UUID]`. The signature is frozen.
- Semantics: returns the ids `user` may see, restricted by `scope` (department / project). Scope only narrows. Result ⊆ provider output. Inactive user → ∅. Empty provider → ∅.
- Ordering rule for every question: AUTHORIZATION → allowed ids → retrieval → LLM. Listing, download, retrieval and `/api/ask` all start from this set; content outside it never reaches a prompt.
- Step 0: single admin, stub returns every existing document. Step 1.2: `employee` = `normal` docs of own departments; `management` = all departments, all confidentiality; `admin` = everything. Document permission derives from department, not project.
- Enforced server-side only; UI hiding is convenience, not security. Any code path bypassing the gate is a bug; tests assert "empty set → empty result".
- **Phase 1.2 implementation:** `DocumentIdsProvider` gained one method, `list_document_ids_for_departments(department_slugs, confidentiality_levels)` — `AuthorizationScope` itself did not change. `documents.department` stays a denormalized slug string with no FK (existing rows/tests predate the `departments` table); a misspelled or unknown slug fails safe — the document becomes invisible to everyone but admin, never exposed. `documents.project_id` gained an FK to `projects.id`. `departments`/`projects` are seed-only in V0 (no department CRUD); project CRUD is admin-only (`require_admin`, `app/api/deps.py`).
- **Aşama C (01.10.2026, B-20/1-5):** the tree was aligned with the product owner's mind map — 5 renames, 4 new rows (`ik`, `enerji_uretim_piyasa`, `mali_isler_muhasebe`, `mali_isler_finansal_muhasebe`), and the demo `finans` user's `mali_isler` membership dropped (P-5). **Slugs did not change** (70 documents, the ledger schema, the eval set and project links all key on them). Departments stay seed/migration-managed — a *platform* action (NOT §5.1 Platform Yetkilendirmesi), still no customer-facing CRUD; the correction for existing databases lives in migration `0010` (every step EXISTS-guarded, a no-op on an empty table) and the seed builds the same tree on a fresh install, with a test proving both paths give one snapshot. The rule itself is unchanged: sub-units are display/filter rows, the authorization unit is the top-level department.
- **Aşama E (01.10.2026, B-26, ADR-023):** the `employee` branch now also includes documents in folders their departments were granted access to — same confidentiality levels, same scope intersection, same single function; see ADR-023.
- **Phase 5.2 concretization — "bu belgeyi kim görebilir" (reverse lookup):** `SingleDocumentIdsProvider` wraps one `Document` as a `DocumentIdsProvider` so `GET /api/documents/{id}/visibility` (admin-only) can run `allowed_document_ids(user, scope, provider)` once per user in the system and keep only those where the target document is in the result — "which users can see this document" without a second rule engine. Fine at V0 scale (a few dozen users); not an approach that scales past that without an index-backed query, which is out of scope here. The same phase adds `/api/users` (admin CRUD for role/`is_active`/department membership, `require_admin`) and `PATCH /api/documents/{id}` (manual metadata edit independent of the Phase 3.2 AI-suggestion flow, same field set minus version-chain fields) — neither introduces a new authorization path; both sit behind the existing `require_admin` gate.
- **Security patch (30.09.2026) — the write side had no membership check:** `POST /api/documents/upload`'s `department` field was validated only against the known-slug list (422 if unknown), never against the uploader's own membership — an `employee` could name any department and plant a document into its retrieval, bypassing this ADR's read-side gate from the write side. Fixed in `documents.py::upload_document`: for a non-`management`/non-`admin` uploader, a given `department` must be one of `current_user.department_slugs`, else `403`. `management`/`admin` stay exempt (the read-side rule already grants them every department); `department=None` is untouched (already fail-safe — invisible to every `employee`, per this ADR's own department-filter rule). Found during a read-only review of `ftansu/AI-BalBal`'s BACKEND_GAPS.md (`docs/notes/TANSU_GERI_BILDIRIM_2026-09-30.md` §2 B-26/3, §3.3); independent of that integration and of the future document-approval workflow described there (§5.2) — one gates *which department* a document can claim, the other will gate *whether it publishes*.
- **B-08 (02.10.2026) — `department_manager` role:** a fourth `user_role` value (migration `0012`, `ADD VALUE`; downgrade rebuilds the type and demotes managers to `employee`). Rule: the `employee` branch with one more confidentiality level — `normal` **and** `restricted` documents of the departments the user belongs to (memberships ∪ B-26 folder grants, both at the same two levels), never `board`, never another department. The rule is fixed code, not a per-customer table (NOT §5.1); the customer admin assigns the role per person through the existing `PATCH /api/users/{id}` (NOT §8.1). No new provider method, signature, table or endpoint; `SingleDocumentIdsProvider` (`/visibility`) takes the levels as a parameter and needed no change. Upload membership check and folder `write` rules treat a manager exactly like an employee (NOT §5.2: `management`/`admin` carry no general privilege, the manager uploads to their own department). Demo: `finans_mudur` (Proje Finans member) — Proje Finans holds the only `restricted` demo document. Decided by Naci (02.10.2026): managers do not see `board`; the role→levels mapping stays a fixed rule; role/membership change events are a separate small job before the §5.2 approval flow.
- **B-28 (02.10.2026, ADR-024) — publication state enters the gate:** every rule above now sees `review_status = approved` documents only (`SqlDocumentIdsProvider`'s three queries filter it; retrieval, search, `/api/ask`, the Excel catalogue and folder counts need no change). `AuthorizationScope.include_pending=True` (document-handling endpoints: list, detail, status, download, suggestion, inspect, supersedes lookup) adds the pending documents the caller may *handle* via one new provider method, `list_pending_document_ids(uploaded_by_id, manager_department_slugs)`: own uploads for everyone, the departments' pending documents for a `department_manager`, every pending document for `admin`; `management` gets none. Still one function; `SingleDocumentIdsProvider` carries the same rule, so `/visibility` of a pending document lists its handlers.

## ADR-005 — `DocumentStore` interface
**Status:** accepted · **Phase:** 0.2
- Files are stored behind a small interface: `store(document_id, filename, stream) -> StoredFile`, `get_file(document_id, kind: original | ocr) -> Path`, `get_text(document_id) -> str`.
- Single V0 implementation `LocalFileSystemStore`: `$APP_DATA_DIR/documents/<uuid>/original.<ext>` and `ocr.pdf`. Metadata has exactly one source of truth: Postgres. Filenames are never a source of metadata.
- No Paperless in V0. Paperless (or SharePoint/OneDrive later) can be placed behind `DocumentStore` in Step 3 if needed; this door is deliberately left open, but nothing in V0 depends on it.
- Rationale: swapping storage must not touch services, authorization or retrieval.

## ADR-006 — Ingestion pipeline and the `ingestion_jobs` queue
**Status:** accepted · **Phase:** 0.2 (pipeline) · 3.2 (metadata suggestion)
- Pipeline: upload → `documents(ingestion_status=uploaded)` + job row → `ocr-worker` (ocrmypdf `--language tur+eng --skip-text --rotate-pages --deskew`; png/jpg converted to PDF first) → page text with PyMuPDF → `document_pages` → chunking → `document_chunks` (+FTS, +vector when enabled) → `ready`.
- The queue is a Postgres table: `ingestion_jobs(status queued|running|done|failed, attempts, error, locked_at, ...)`; the worker polls with `SELECT … FOR UPDATE SKIP LOCKED`, max 3 attempts, then `failed` with a Turkish reason on the document.
- No Redis/Valkey/Celery: one extra container and one table are enough at this scale, and the queue is backed up with the database.
- LLM metadata suggestion (Phase 3.2) runs after `ready`; its failure never fails the upload.
- **Phase 4.2:** the Excel family (`xlsx`/`xlsm`/`csv`) bypasses this pipeline entirely — no job row, no OCR, no pages/chunks; the upload marks the document `ready` (sheet count as `page_count`). `ocr-worker` still defends itself: an Excel job, should one ever appear, is finished as `done` without calling ocrmypdf.
- **Phase 3.2 concretization:** `ingestion_jobs` stays OCR-only (no `job_type` column, YAGNI) — the metadata-suggestion queue is a plain SQL predicate (`ingestion_status=ready AND ai_suggestion_id IS NULL`), not a second job table. Two entry points share `app/services/metadata_suggestion.py::suggest_metadata()`: an admin-only `POST /api/documents/{id}/suggest-metadata` (idempotent while `pending`/`applied`; explicit retry after `failed`/`rejected`) and an in-process `asyncio` background scan (`app/main.py` lifespan, `metadata_suggestion_poll_interval_s`/`_batch_size`) that never starts against a `_test` database, so `make test` never calls the LLM through this path. `document_metadata_suggestions.document_id` is unique (one row per document, overwritten on retry — no suggestion history in V0). `documents.ai_suggestion_id` deliberately carries **no FK** to it: a real one would cycle with that table's own FK back to `documents.id` (SQLAlchemy cannot topologically sort the pair); it is kept in sync by the service only, used purely as an existence flag.

## ADR-007 — Retrieval: full-text + metadata first, embeddings behind a flag
**Status:** accepted · **Phase:** 0.2 (FTS) · 3.4 (hybrid)
- Default retrieval is Postgres FTS (`tsvector` with `turkish` and `simple` configurations) plus metadata filters (department, project, document_type, dates, status).
- `EMBEDDINGS_ENABLED=false` is the reference configuration: the whole system and test suite must pass without the `embed` service.
- With the flag on, bge-m3 vectors in `document_chunks.embedding` (pgvector) are combined with FTS (hybrid); the `embed` container runs only under `--profile full` (16 GB VM).
- Retrieval always receives the allowed-id set first (ADR-004) and filters at the SQL level, never after the fact.
- **Phase 3.4 concretization:** `retrieve()` fuses FTS and vector results with Reciprocal Rank Fusion (k=60; rank position only, never raw scores — `ts_rank_cd` and cosine similarity live on incomparable scales). A dead/slow `embed` service degrades retrieval to FTS-only (`EmbeddingError` caught, warning logged) rather than failing `/api/ask` — live-verified by stopping the `embed` container mid-session and confirming a 200 response (SPEC_06 §8). A background loop (`app/main.py`, same pattern as Phase 3.2's metadata scan) backfills `document_chunks.embedding` in batches; `ocr-worker` stays unaware of `embed` entirely. No pgvector ANN index (ivfflat/hnsw) yet — at V0's chunk count (dozens–low hundreds) a plain `<=>` scan is fast enough; add one if Phase 5.1's dataset makes it necessary. **Measured RAM was ~10.5 GB for the `embed` container alone (`docker stats`), well above the ~3-4 GB estimated from bge-m3's published weight size — TEI's CPU runtime overhead (batch buffers, ONNX runtime, tokenization workers) is the difference.** Still fits the 16 GB dev VM (`free -h` showed ~4 GB available with everything else running) but leaves less headroom than planned; `docs/reports/PHASE_3_4_REPORT.md` has the full numbers.

- **Phase 3.2b concretization (hybrid diagnosis):** with both legs capped at `top_k`, RRF (k=60) can never rank a chunk found by one leg only above a chunk found by both (`1/61 < 2/(60+top_k)` for any `top_k < 62`), so a page only the vector leg finds was cut — that, not embed quality or latency (measured 40–190 ms, no fallback), is why Phase 4.1's embedding probe showed no gain. `retrieve()` now fetches each leg at `2×top_k` and cuts after fusion. On the 43-question golden set hybrid retrieval adds no measurable page recall over glossary-expanded FTS (both 100% on the 20 measurable questions), so `EMBEDDINGS_ENABLED=false` stays the reference configuration; the `retrieval explain` log line (per-leg timings and page lists) is the tool for revisiting this at Phase 5.1 scale.

## ADR-008 — Page-level sourcing
**Status:** accepted · **Phase:** 0.2
- `document_pages(document_id, page_number, text)` keeps page text; chunks never cross a page boundary and `document_chunks.page_number` is NOT NULL.
- Chunk size ≈ 800 tokens with 100 overlap inside a page.
- Every document-based answer cites document title, **page**, document date, version and project; the audit log stores the same citation.
- Rationale: auditability (rule 4) requires that a human can open the PDF at the cited page.

## ADR-009 — LLM client
**Status:** accepted · **Phase:** 0.3
- `LLMClient` protocol with `OpenAICompatibleClient` (openai SDK + `base_url`; default Gemini at `https://generativelanguage.googleapis.com/v1beta/openai/`) and optional `AnthropicClient`.
- Two model settings: `LLM_MODEL_CLASSIFY` (cheap, metadata suggestion / routing) and `LLM_MODEL_ANSWER`. Defaults from the official model list at the time of writing: `gemini-3.5-flash-lite`, `gemini-3.8-flash`.
- Thinking/reasoning kept low (`LLM_REASONING_EFFORT`, default `low`), output tokens capped; token counts in/out logged per call (`llm call` record) and, from Phase 3.4, written to the audit log. Gemini's OpenAI endpoint reports no separate reasoning-token count (`tokens_reasoning` stays null).
- The LLM receives only allowed chunks (ADR-004), never does arithmetic (ADR-011), and cannot execute code.
- No LangChain/LlamaIndex: prompts and retrieval are explicit and testable.
- Phase 0.3 decision: `AnthropicClient` is deferred; `LLM_PROVIDER=anthropic` raises a clear "not configured" error until the Phase 4.3 model decision point. Vendor errors are mapped to an `LLMError` hierarchy; the API answers 503 with a fixed Turkish message and never exposes provider detail.
- **Phase 3.2 concretization:** `LLMRequest` gained an optional `response_format: "text" | "json_object"` (default `"text"`, unchanged for `/api/ask`); `OpenAICompatibleClient` passes it through as the OpenAI-typed `ResponseFormatJSONObject` param, omitted (`openai.Omit()`) rather than sent for the default case. Metadata classification (`metadata_suggestion.py`) is the only caller that sets `"json_object"`.

## ADR-010 — Question router
**Status:** accepted · **Phase:** 4.3 (simple version in 0.3 answers DOCUMENT only)
- Query types: `DOCUMENT_QUERY | DATA_QUERY | MIXED_QUERY | GENERAL_QUERY`.
- MIXED = two sub-queries (document + Excel) merged without interpretation. Ambiguous "current DSCR?" → covenant (document) and actual (Excel), two source types.
- GENERAL uses no company data and says so in the answer.
- The router is a service with a fixed interface so future "Email AI" can be added without touching callers (SPEC_01 §8) — but only the two V0 branches exist.
- **Phase 4.3 concretization:** `app/services/router.py` — `Router` Protocol (`route(question) -> RoutedQuestion{query_type, document_question, data_question}`) with one implementation, `LLMRouter`: a single `LLM_MODEL_CLASSIFY` call, `response_format=json_object`, few-shot with the SPEC_04 §7 examples plus the explicit rule "ambiguous contractual-vs-realised value → MIXED with two self-contained sub-questions". DOCUMENT/DATA always run the *original* question (retrieval/planning unchanged by the router); only MIXED uses the rewritten sub-questions. Every failure (LLM error, malformed JSON, unknown type) degrades to `DOCUMENT_QUERY` — the safe direction: a wrongly-GENERAL answer would drop company sources. `app/services/ask_router.py::answer_routed_question` runs the pipelines **unchanged** (`ask.answer_question`, `excel_ask.answer_data_question`, both with `write_audit=False`) and merges MIXED deterministically under two fixed Turkish headings (`Belgelere göre:` / `Excel verisine göre:`) — no third LLM call, both branches always run, a branch that found nothing keeps its fixed "not found" text so the model never silently picks a side. GENERAL (`app/services/general_answer.py`): no `allowed_document_ids`, no retrieval, no workbook; the fixed notice is prepended by code; a reply that names a project (from the `projects` table) or contains a money amount is dropped for a fixed text (leak guard). `AskResponse` grew backwards-compatibly (`query_type`, `excel_sources`, type-specific `notice`); `sources` keeps meaning document pages. `POST /api/excel/ask` stays as the router-less DATA endpoint (SORU 5). **DATA miss falls through to documents:** when the Excel branch of a `DATA_QUERY` answers nothing (no visible workbook, plan `none`, unknown period), the original question runs through the document pipeline and the row/response carry `DOCUMENT_QUERY` — the first eval run showed the router tagging contract-stated amounts ("yerli banka kredisi ne kadar?") as DATA and dead-ending in "Excel'de bulamadım"; with the fall-through a mis-routed question costs one extra call and behaves exactly as before the router.
- **Phase 5.1 concretization:** `questions.json`'s `general` category (3 questions) closes the "eval doesn't cover GENERAL" gap Phase 4.3 left open — `scripts/eval_lib.py::score_question` scores it on `query_type == GENERAL_QUERY` + zero cited sources, not on a ledger value (there is none), at the default 80% threshold.
- **GENERAL_QUERY removed (30.09.2026, Naci + Tansu):** the fourth type is gone — `QueryType` is now `DOCUMENT_QUERY | DATA_QUERY | MIXED_QUERY` and `app/services/general_answer.py` was deleted. This was a deliberate scope decision, not a bug fix: the system must never again answer from the model's own world knowledge, including definition questions ("DSCR ne demek?") — that had been GENERAL_QUERY's one carved-out exception to rules 2 (SOURCE GROUNDING) and 6 (NO OPINION), and closing it is a correction, not a new conflict. Every question now goes through DOCUMENT_QUERY (or DATA/MIXED); the existing zero-source fixed-text path (ADR-014, ADR-021) already covers "no document defines this term" without any new mechanism — live-verified: the 3 former `general`-category eval questions (now `category: document`, `expect_no_answer: true`) route to `DOCUMENT_QUERY` and return the exact fixed "bilgi bulamadım" text against the real demo corpus, which never defines these terms generically. `answer_prompt.py` gained one new rule (9): if multiple *unrelated* sources define the same term differently (not a `supersedes` chain — rule 5 still owns that), relay all of them labelled, never pick one. Detail: `docs/plans/GENERAL_QUERY_KALDIRMA_PLAN.md`, `docs/reports/GENERAL_QUERY_KALDIRMA_REPORT.md`.
- **Aşama B (30.09.2026, B-20/6):** `AskRequest.project_id` and `ExcelAskRequest.project_id` were removed — one conversation may span projects; the answer keeps them apart by citing sources. Pydantic's default `extra="ignore"` keeps older clients on 200. `audit_log.scope_project` stays a column (historical rows) and is `NULL` for every new `/api/ask` row; `RetrievalFilters`/`AuthorizationScope.project_id` and `GET /api/documents?project_id=` are untouched. The eval set never sent `project_id`, so the isolation score was already measured without the filter.
- **Aşama A concretization (30.09.2026):** `product_level` is derived from the *final* type in `ask_router.py` (`PRODUCT_LEVEL_BY_TYPE`), and a DATA/MIXED routing is degraded to DOCUMENT with the original question when P2 is not enabled — see ADR-022. `RoutedAnswer`/`AskResponse` gained `audit_log_id`, `product_level`, `warnings` (all additive).

## ADR-011 — Excel engine boundaries
**Status:** accepted · **Phase:** 4.2
- Inspection with openpyxl (`data_only=True` cached values, formulas, named ranges, hidden sheets); calculation with DuckDB (in-memory, read-only, `enable_external_access=false`, 10 s timeout, row limit); Polars for transformations.
- The LLM decides *what* to compute: either parameters of predefined functions (`dscr`, `outstanding_debt`, `budget_variance`, `capacity_factor`, `production`) or a single whitelisted `SELECT` (no `;`, known tables only, `LIMIT` added, `COPY/ATTACH/INSTALL/LOAD/PRAGMA` rejected). The final number never comes from the model.
- `.xlsm` macros are never executed. No LLM-written Python is executed.
- **Aşama B (30.09.2026, B-17):** `GET /api/documents/{id}/download` names the file after the document title (control/path/Windows-reserved characters stripped, 120 chars, Turkish letters kept — Starlette emits RFC 5987 `filename*`), sets `Content-Type` from an explicit extension map (the container's `mimetypes` has no xlsx/xlsm) plus `X-Content-Type-Options: nosniff`, and honours `?inline=1` only for pdf/image (always the original bytes, never the OCR copy); workbooks/CSV stay attachments. Authorization path unchanged (403).
- `CalculationEngine` interface with one implementation, `CachedValueEngine`; missing cached values produce a user message, not a server-side recalculation (LibreOffice recalc is a build step for demo files only).
- Every Excel answer cites `file + sheet + range`.
- **Aşama B (30.09.2026, B-13):** `Document.file_kind` (`pdf | image | xlsx | xlsm | csv`) is a property derived from `storage_path`'s extension — every stored file was content-sniffed at upload into that closed set, so no column and no migration; `None` only for a hand-edited row. Exposed on list/detail/upload responses so a client can tell a workbook from a PDF without probing `/inspect`.
- **Phase 4.2 concretization:** `backend/app/excel/` — `inspect.py` (openpyxl, two loads: `data_only=True` values / formulas; macro presence read from the zip member `xl/vbaProject.bin`, never from the extension, never loaded), `sql_guard.py` (pure whitelist: no `;`/comments, `SELECT`/`WITH` only, forbidden keyword and file-function token list, `FROM/JOIN` names must be known tables, `LIMIT` capped at `EXCEL_ROW_LIMIT`), `calc.py` (`CalculationEngine` Protocol + `CachedValueEngine`: visible sheets → Polars → DuckDB tables `<file>__<sheet>` with an `_row` column carrying the Excel row number, `enable_external_access=false`, `conn.interrupt()` after `EXCEL_QUERY_TIMEOUT_S`; a workbook with uncached formula cells raises `NeedsRecalculationError` → user message, no server-side recalc), `functions.py` (`dscr`, `outstanding_debt`, `budget_variance`, `capacity_factor`, `production` read named ranges — the contract with `generate_excel.py` — and cite the cell/range). Two LLM calls in `services/excel_ask.py`: a planning call (`LLM_MODEL_CLASSIFY`, JSON: function+params | one SELECT | none) over a catalogue of the workbooks the user may see (ADR-004 first), and a phrasing call (`LLM_MODEL_ANSWER`); if the phrased answer does not contain the engine's number verbatim, a template answer is returned — the final figure never comes from the model, measurably. Excel-family uploads (`xlsx`/`xlsm`/`csv`, sniffed from bytes) are `ready` at once, get no OCR job and no chunks (SPEC_04 §1); `documents.has_macros`/`file_name` (migration 0008). ## ADR-014 — "No opinion" rule (V0)
**Status:** accepted · **Phase:** 0.3
- The system finds, reads and relays. It produces no opinion, projection, recommendation or speculation.
- Fixed strings: no source → "Mevcut şirket kaynaklarında bu soruyu güvenilir şekilde cevaplamak için yeterli bilgi bulamadım."; "why?" without a stated reason in the documents → "belgelerde sebep belirtilmemiş".
- The answer UI states briefly that answers contain no interpretation.
- Rationale: trust is built on verifiable relay before any reasoning feature is considered.
- **Ürün 1 uyum turu (01.10.2026, Balbal Anayasası v2.0 Ü-3 / Ç-7):** rule 10 — a question spanning several projects gets each project's value in its own sentence with its own source; no comparison, ranking, "hangisi daha …" judgement, difference or ratio; an explicit comparison request is answered with the fixed `COMPARISON_NOTICE` ("Projeler arası karşılaştırma bu üründe yapılmaz; değerler ayrı ayrı aşağıdadır.") followed by the separate values. The rule holds in every package (Naci; whether Ürün 2 may compare is an open question for Tansu). Live before the rule: the model wrote "İzmir RES'in kurulu gücü daha büyüktür" — a comparison is a judgement, i.e. an opinion in this ADR's sense. Measured with the new `comparison` eval category (100% threshold, phrase checks, `--repeat 3`). Same round: the no-answer outcome is now two states on the wire — `missing_data` (nothing retrieved) and `insufficient_data` (documents retrieved, model declined) — the fixed text itself is unchanged; the 4-step Ç-7.1 protocol is deferred to a separate UX phase.
- **Phase 3.2 concretization:** live testing surfaced a real ambiguity between this rule and rule 2 ("kaynaklar yetmiyorsa" → the no-source sentence) — a model asked "neden değiştirildi?" about a fact that *is* in the sources (only the cause isn't) sometimes fell back to the generic no-source sentence instead of "belgelerde sebep belirtilmemiş". `answer_prompt.py`'s rule 6 now explicitly says which sentence wins when the topic itself is present but its cause isn't; `backend/tests/live/test_ledger_live.py::test_why_question_without_stated_reason_returns_fixed_text` is the regression test (`make test-llm`).

## ADR-016 — Audit log is not corporate memory
**Status:** accepted · **Phase:** 3.4
- `audit_log` records who asked what, when, with which scope, which documents/Excel ranges were used, the answer, model and token counts, `request_id`, errors.
- Visible only to admins; retained 90 days with a daily cleanup; never used by retrieval or prompts. One user's questions never influence another user's answers.
- Passwords, API keys and JWTs are never written to it.
- **Phase 3.4 concretization:** one row is written per `/api/ask` call from `app/services/ask.py::answer_question()` itself (not the API layer) — the zero-chunk "no answer" path, the LLM-answered path and the LLM-error path (`error` set, response still the existing 503, unchanged) all write a row; a broken audit write never breaks the answer already computed (same "never breaks the caller" pattern as Phase 3.2's metadata suggestion). Retention/cleanup: a background loop (6 h interval — a cheap idempotent `DELETE ... WHERE timestamp < cutoff` comfortably satisfies "daily") plus `python -m app.cli cleanup-audit-log` for a host cron or one-off run. Admin-only read API: `GET /api/audit-log` (filtered list, no `answer`/`sources`) and `GET /api/audit-log/{id}` (full record) — the UI on top is Phase 5.2. `cost_estimate` stays `NULL` in V0: no invented per-model pricing table.
- **Phase 4.2:** `POST /api/excel/ask` writes its own row (`query_type=DATA_QUERY`, `excel_files_used`, `sources` = file/sheet/range cards, `documents_retrieved` = the cited workbooks); a rejected SQL plan is logged with `error="sql rejected: …"`.
- **Phase 4.3:** one `/api/ask` call = one row, whatever the type (SORU 2): the single write path is `app/services/audit_writer.py::write_audit_row`, called by the router orchestrator (the sub-pipelines run with `write_audit=False`) or by each pipeline when it is the entry point itself. `query_type` is now the real router decision; `sources` JSONB cards carry `kind: "document" | "excel"` so a MIXED row's two source kinds stay distinguishable; `documents_retrieved` = retrieved document ids + cited workbook ids; `chunks_retrieved` from the document branch; `tokens_*` include the router call. An LLM failure inside any branch writes the row with `error` (and the router's type) before the 503 propagates. GENERAL rows have empty `documents_retrieved`/`sources`/`excel_files_used` — the measurable form of "no company data used".
- **Phase 3.2b concretization:** `chunks_retrieved` (JSONB, migration `0007`) records the `(document_id, page_number, rank)` of every chunk that reached the prompt — `documents_retrieved` alone could not tell a retrieval miss (right document, wrong page) from a model refusal, which is exactly the distinction Phase 4.1's failures needed. - **Phase 5.2 concretization:** the admin UI promised above (`AdminAuditLogPage`) is built — a filter form whose fields map one-to-one onto `GET /api/audit-log`'s existing query parameters (`user_id`/`department`/`project_id`/`query_type`/`from_ts`/`to_ts`/`has_error`, plus `limit`/`offset` pagination), and a row-click detail view backed by `GET /api/audit-log/{id}`. No backend change — the filtering/pagination/heavy-field-split behaviour this ADR already describes was correct as specified.
- **Aşama A concretization (30.09.2026):** `write_audit_row` returns the new row's id and `/api/ask` returns it as `audit_log_id` (the "cevap kimliği" half of B-04; the row is still readable only through the admin API, so the id grants nothing). Two columns (migration `0009`): `product_level` and `warnings` (JSONB) — stored per row, not derived, so a later change to the type→layer mapping never rewrites history; rows written before 0009 stay `NULL`/`[]`, no backfill guess. `AuditLogDetail` exposes both.

## ADR-020 — Search query construction: OR semantics for natural-language questions
**Status:** accepted · **Phase:** 0.3
- `websearch_to_tsquery` ANDs terms; a Turkish question ("Ankara RES'in güncel minimum DSCR covenant'ı nedir?") against English contracts therefore matched **zero** chunks (measured on the live DB before Phase 0.3).
- `app/services/search_query.py::build_search_query()` strips apostrophe suffixes (`RES'in → RES`), drops a small Turkish question-word/particle stoplist and duplicates, and joins the rest with `OR`. Lower-casing and stemming stay in Postgres (`turkish` / `simple`), consistent with indexing.
- Ranking uses `ts_rank_cd` (cover density): chunks where several distinct query terms occur together outrank cover pages that merely list the words. `search_fts()` and `retrieve()` keep their signatures; the repository never sees question text, only the built query.
- Consequence (deliberate): a question about a project with no documents (İzmir RES) still retrieves chunks of another project through shared terms ("RES"). Project isolation is then the LLM's rule-2/3 discipline (ADR-021) until the structural `project_id` filter arrives with the `projects` table (Phase 1.2). Phase 4.1's `isolation` eval category must cover exactly this scenario.
- Embeddings (ADR-007, Phase 3.4) will add semantic recall; this ADR governs the FTS leg only.
- **Aşama D (01.10.2026, B-14):** `GET /api/search` reuses the same FTS predicate as retrieval through `document_chunk_repo._fts_predicate` (shared by `search_fts` and the new `search_document_hits`), so what the search box finds is what Balbal would retrieve; `retrieve()`/`search_fts` themselves are unchanged (eval unaffected). Search adds what retrieval never needed: one hit per document (`DISTINCT ON`, best-ranked page) and a plain-text `ts_headline` snippet (`StartSel="", StopSel=""` — the chunk text is user-uploaded, so the UI never renders HTML from it), merged with title/type/counterparty/`external_ref` ILIKE hits, plus projects (`GET /api/projects` visibility) and people (`search_directory`). Documents only from `allowed_document_ids`; no `audit_log` row (ADR-016 records questions, not searches).
- **Phase 3.2b concretization:** Phase 4.1's eval showed the OR query's real failure mode is *cross-language*: a Turkish question ("finansman", "kredi") shares no lexeme with the English page that states the figure, so that page ties with ~27 others at the lowest matching rank and `LIMIT top_k` picked the winners by heap order — the same question could reach the LLM with a different page set on each call. Three fixes, all on the FTS leg: (1) `app/services/search_glossary.py` — a curated energy-project-finance glossary (Turkish stem → English document terms, and the reverse) ORed into the query by `build_search_query()`; not a list of the golden questions' words; (2) a deterministic tie-break `(rank DESC, document_id, chunk_index)` in `search_fts`/`search_vector`; (3) `retrieval_top_k` 20 → 40 (the corpus is one page per chunk, ~450 chars, so 40 chunks ≈ 10k tokens). Measured with the LLM-free `run_eval.py --retrieval-only` probe: page recall@20 18/20 → 20/20 with (1)+(2) alone.

## ADR-021 — Answer pipeline: deterministic temporal evaluation, cited sources, no-LLM fallback
**Status:** accepted · **Phase:** 0.3
- Order per question (SPEC_02 §9): `allowed_document_ids` → `retrieve()` → load the `supersedes` chains of the retrieved documents (restricted to allowed ids at every hop) → `evaluate_version_chains()` → prompt → LLM → parse citations. Only chunk text from `retrieve()` ever enters the prompt.
- **Temporal truth is computed in code** (`app/services/version_chain.py`): `is_current` = last chain link in force on `DEMO_TODAY` (effective_date or document_date ≤ today, not expired, not superseded by a hidden document); `is_initial` = first link. The prompt carries these as `Zincir: GÜNCEL / İLK HALKA …` headers, current documents first; the model reads them, never derives them. Old values are relayed as historical, never as wrong (ADR-012).
- Sources are what the model cites: every source block is labelled `[K<n>]`; the answer must end factual sentences with labels; `parse_citations()` maps labels back to (document, page). Unknown labels are dropped and logged. Plain text + labels was chosen over JSON mode (simpler parsing, no escaping issues with Turkish text).
- No retrieved chunk → the fixed "bilgi bulamadım" answer is returned **without calling the LLM** (zero tokens). A model reply containing the no-answer sentence is canonicalised to the exact fixed string with `answered=false` and no sources (ADR-014).
- The response also carries `retrieved_document_ids` (for tests, the Phase 4.1 eval and the Phase 3.4 audit log) and a fixed notice that answers contain no interpretation.
- Version chains are created at upload time via optional `effective_date` / `version` / `supersedes_document_id` fields; the predecessor must be visible to the uploader and not already superseded (409); its `status` is not changed (Phase 3.2 owns status transitions).
- `GET /ask` serves a single-file HTML test page from the backend (no Caddy, no build); it stays as a developer page after the real frontend (Phase 3.3).
- **Phase 4.3:** `POST /api/ask` now enters through the router (ADR-010) before this pipeline; the pipeline itself is unchanged and, for `DOCUMENT_QUERY`, receives the original question verbatim.
- **Aşama D (01.10.2026, B-20/6):** `SourceCard` also names the document's project (`project_code`, `project_name`, `None` for project-less corporate documents) through a `Document.project` relationship — the UI no longer derives it from a second `/api/documents` request. Organisational information only; permission still comes from `department` (ADR-004).
- **Aşama A concretization (30.09.2026, B-07):** `SourceCard` carries `supersedes_document_id` / `superseded_by_document_id` next to the titles, plus `is_initial`. No new authorization code: `ChainPosition` resolves neighbours from the documents `load_with_chains` loaded, and that loader already drops any hop outside `allowed_document_ids` — a neighbour the user may not see is never loaded, so its title *and* id are `None` and the visible link is not called current (tested with a `restricted` amendment and a `finans` employee).

## ADR-023 — Folders and department access grants (B-26)
**Status:** accepted · **Phase:** Aşama E (01.10.2026, no phase tag — `docs/plans/ASAMA_E_PLAN.md`)
- The company's own system administrator builds the folder tree and grants from the admin screen (Tansu, 01.10.2026: "hepsini bizim oluşturacağımız araçtan admin belirler") — *Personel Yetkilendirmesi* in the note's §8.1 terms; the backend imposes no structure beyond one root folder per top-level department (migration `0011` for existing databases, `seed-demo-folders` for fresh ones; the richer demo tree is B-18).
- Data: `folders(id, name, parent_id, owner_department_id)`, `folder_grants(folder_id, department_id, access read|write)`, `folder_grant_events(actor, folder, department, before, after)` and `documents.folder_id`. A document lives in one folder and its `department` **is** the folder owner's slug (set server-side on upload; a contradicting `department` is 422) — ADR-004's "permission derives from department" is unchanged. A sub-folder's owner always equals its parent's; one name per level; a folder with documents or children cannot be deleted (409).
- Inheritance: a department's effective access on a folder is the **nearest ancestor-or-self definition**; `PUT …/grants` with `none` removes a definition so the parent's applies again. There is no explicit "deny below"; `write ⊇ read`; the owner is never a grant. The rule is a pure function (`services/folder_access.py::FolderAccessMap`) over the whole tree (dozens of rows), unit-tested on plain data and shared by the gate provider, the admin API, the user view and the upload check.
- **Single gate kept:** `allowed_document_ids` signature unchanged; `DocumentIdsProvider` gained one method, `list_document_ids_for_folder_grants(department_slugs, confidentiality_levels)`, and the `employee` branch is `membership ∪ folder grants`, still intersected with scope and still limited to `normal` confidentiality — a grant never lifts confidentiality (§2.6.1/6). `management`/`admin` are untouched (they already see everything). `SingleDocumentIdsProvider` takes the document's effective grantee departments so "kim görebilir" stays consistent. The gate is computed per request with no cache, so a revoked grant hides documents in the very next request (§2.6.1/9) — list, search, download and Balbal retrieval all go through the same set.
- Write side: upload with `folder_id` requires owner membership or an effective `write` grant (`management`/`admin` always); the `write` grant does **not** yet cover metadata editing (`PATCH /api/documents/{id}` stays admin-only until B-28 redefines editing rights).
- Audit: grant changes are not `audit_log` rows (ADR-016 records questions); `folder_grant_events` keeps one row per *effective* change with before/after values, read by `GET /api/admin/folders/audit`. No retention.
- Endpoints match AI-BalBal `proposed.ts` §10 field for field (`AdminFolder`, `FolderGrant`, `UserFolder`, `FolderAuditEntry`): `GET/POST/PATCH/DELETE /api/admin/folders`, `PUT …/{id}/grants`, `GET …/audit`, `GET /api/folders` (per-user tree with effective access and the count of documents *that user* can see). `GET /api/admin/access-matrix` is not implemented — the UI derives the matrix from `grants`.

## ADR-024 — Document publication state and the two-stage approval (B-28)
**Status:** accepted · **Phase:** B-28 round (02.10.2026) · supersedes Phase 3.2 SORU 2 ("publishing = admin `apply`")
- A document carries `documents.review_status ∈ {pending_metadata, pending_review, changes_requested, approved}` — a fourth axis beside `ingestion_status` (file pipeline), `status` (legal lifecycle) and the AI suggestion's own status. Only `approved` documents are corporate memory: retrieval, search, `/api/ask` and the Excel catalogue see nothing else (NOT §3.3, Naci 30.09.2026). The filter lives inside `allowed_document_ids` (ADR-004), never beside it.
- Who publishes without review: **only the target department's own `department_manager`** (member of the document's department) — their upload is `approved` at once (`auto_approved` event). Everyone else — `employee`, `management`, `admin`, another department's manager — goes through two stages (NOT §5.2, Tansu #5 + Naci): (1) `POST /api/documents/{id}/submit` by the **uploader only** (admin may not act for them, P-1): final metadata, AI suggestion marked `applied`, `pending_review`; (2) `POST /api/documents/{id}/review` by the target department's manager: `approve` → `approved`, or `request_changes` with a mandatory comment → `changes_requested` → the uploader resubmits. No terminal `rejected` state (Naci SORU 3).
- Confidence threshold (BACKEND_GAPS §4.7.5): a suggested value below `METADATA_CONFIRM_THRESHOLD` (default 0.8) that is kept as suggested must be named in `confirmed_fields`, else 422 `low_confidence_not_confirmed`; a changed value is an explicit decision by itself. The rule is enforced by the server, not left to the UI. OCR documents need their suggestion to exist first (409 `suggestion_pending`); a workbook has no suggestion and is confirmed from the typed fields. A department-less document cannot be submitted (422 `department_required`) — it would have no approver.
- No configured approver → the upload itself is refused with 409 `approver_not_configured` before the file is stored (Naci SORU 1a); a department-less upload is accepted and waits in the admin's handling view. There is no admin fallback approver and no `management`/`admin` exemption (NOT §5.2).
- Editing an approved document's metadata (`apply`, `PATCH`) reopens the review (`pending_review`, event `metadata_changed_after_approval`) unless the actor is the target department's manager (T9, Naci SORU 4). `apply` stays admin-only but is no longer a publishing act.
- Ledger: `document_review_events` (append-only; uploaded, auto_approved, field_edited, field_confirmed, submitted, resubmitted, approved, changes_requested, metadata_changed_after_approval; before/after/confidence/comment). Not `audit_log` (ADR-016). Read by `GET /api/admin/documents/{id}/review-events`, admin-only (§4.7.6). Python-side `created_at` so several events in one request stay ordered.
- `DocumentDetailResponse.uploaded_by_id` (02.10.2026, AI-BalBal PR-2): the detail view carries the uploader so the UI shows the stage-1 action only to them; authorization stays server-side (`not_the_uploader`).
- Queue without B-01: `GET /api/documents?review_status=a,b` (handling view) is the uploader's "my pending" and the manager's "waiting for me"; the future agenda wraps it as `kind: approval`.
- Existing data: migration `0013` adds the column with DEFAULT `approved` — the 70 demo documents + 4 workbooks stay published; seed, ocr-worker and direct `Document(...)` rows are unaffected. Only `POST /api/documents/upload` creates pending rows.
- Error contract: `detail = {"code", "message"}` (machine-readable code + Turkish sentence; the AI-BalBal client renders `detail.message`), codes: `approver_not_configured`, `suggestion_pending`, `review_state_conflict`, `not_the_uploader`, `not_the_approver`, `comment_required`, `not_processed`, `department_required`, `low_confidence_not_confirmed`.
- Out of scope (B-28b): `extra_fields`, tag catalogue, per-type field guide, folder suggestion, "placement approval" for a folder without write access (§4.7.9/1). → done in ADR-025 (02.10.2026) except the folder suggestion and the placement approval.

## ADR-025 — Extra fields, tag catalogue and document-type guide (B-28b)
**Status:** accepted · **Phase:** B-28b round (02.10.2026) · builds on ADR-024
- **Principle (NOT §5.1/§8.1, BACKEND_GAPS §4.7.2–4.7.4):** the *structure* a company classifies with — its tag list and its per-type guide — is customer-admin-managed data; the *rules* stay in code: a tag must come from the active catalogue (strict, 422 `unknown_tag`), extra fields are capped and normalised, the guide only steers and never blocks a submission ("sabit form yok").
- `documents.extra_fields JSONB` — `{key: {value, source: ai|user, confidence, added_by_id, added_at}}`; keys `snake_case` (Turkish letters folded), ≤ 20 per document, string values only (rule 3: no arithmetic in metadata). `source=ai` when the kept value equals Balbal's suggestion, else `user`; a key Balbal did not suggest is a staff addition → `document_review_events.kind = field_added` (§4.7.3 "personel ekledi"). The §4.7.5 confidence rule applies per extra key under `confirmed_fields: ["extra_fields.<key>"]`.
- `tag_catalog(slug, label, kind: identity|change, is_active)` — admin CRUD `/api/admin/tags`, everyone `GET /api/tags`; retire with `is_active=false`, never delete. Classifier output is filtered to the active catalogue; what it proposed outside is kept as `fields.tags.dropped` for the admin to see. Starter: the nine §4.7.4 change tags + every tag already in use (identity) — migration `0014` data step and `demo_catalog_seed` give one snapshot.
- `document_type_guide(family, type_patterns, suggested_extra_fields, suggested_tags, standard_fields_emphasis, prompt_hint)` — admin CRUD `/api/admin/document-type-guide`, everyone reads the active rows; `type_family.match_family` picks the longest matching pattern ("Licence Amendment" → amendment). Starter families: contract, amendment, licence_permit, report, resolution_minutes, insurance, correspondence, invoice, workbook, other — keys from §4.7.2 and the ledger's `parties`/`key_facts` names; configuration, not ledger data. `GET /api/admin/document-type-guide/signals` counts staff-added keys per family (§4.7.3) — a human decides whether the guide changes.
- Classifier prompt gains the active tag list and the guide block and returns `extra_fields`; `_sanitize` normalises keys, caps at 20, drops unknown tags. `format_source` adds one line (`Muhatap | Etiketler | Ek alanlar`) when present — the system prompt (rules 1–10) is unchanged. `/api/search` metadata hits include tags and extra-field values, with `SearchDocumentHit.matched_on`. Retrieval *ranking* is unchanged (Naci SORU 4; a metadata tsvector is a later ADR-007 change).
- `admin_events(kind, actor, target, before, after)` — append-only ledger for configuration changes (tags, guide; role/membership changes join it later — B-08 SORU 2). Not `audit_log` (ADR-016).
- Demo: the ledger's `parties` are seeded as `extra_fields.parties` (`source=user`), once, only when nothing is recorded yet (Naci SORU 2); `key_facts` stay eval references.
- Not here: folder suggestion (B-26 tree in the prompt + §4.7.9/1 placement approval) and AI-BalBal UI (PR-5: tag picker, extra-field rows, admin catalogue/guide pages).

## ADR-026 — Real calendar vs demo calendar; date arithmetic out of the LLM prompt

**Status:** accepted · **Phase:** cross-cutting round (05.10.2026) · plan `docs/plans/TARIH_SAAT_PLAN.md`
- **Problem (live diagnosis, 02.10.2026):** `Settings.demo_today` was the system's only "today", read directly in two places (`ask.py`, `version_chain`'s consumer); nothing distinguished it from a future real-calendar deployment, and rule 8 of `answer_prompt.SYSTEM_PROMPT` told the model to compute date differences itself ("use BUGÜN for 'currently'/'which year'") — the same kind of arithmetic rule 3 (CALCULATION) forbids everywhere else. Separately, `outstanding_debt('today')` read a workbook value frozen at generation time with no check that it still matched "today".
- **Single entry point:** `app.services.temporal.today(settings)` — the *only* place `Settings.demo_today`/`company_timezone` are read. `demo_mode_enabled: bool = True` (default, unchanged behaviour) selects `demo_today`; `False` selects `datetime.now(ZoneInfo(company_timezone)).date()`. Rollback to the real calendar is the one flag `DEMO_MODE=false`; no other code path touches the wall clock for "current/historical/which year" decisions. Verified in the running image: `zoneinfo` resolves `Europe/Istanbul` with no extra `tzdata` package (the base image already carries `/usr/share/zoneinfo`).
- **Rule 3 extended to dates:** `temporal.expiration_note(document, today)` is a pure function — a ready-made Turkish sentence ("Süre: … tarihine kadar yürürlükte (N gün kaldı)" / "… tarihinde sona erdi (N önce)"), appended by `format_source()` only when `expiration_date` is set (older sources stay byte-identical, same pattern as `describe_metadata`). Rule 8 now tells the model to use this line as given and never compute a date difference itself; a question with no ready-made line gets "veri yok", not a guess.
- **`documents.expiration_date`** (column already existed, ADR-012) now has a ledger counterpart: `ledger_schema.Document.expiration_date: Fact | None`, carried through `generate_documents.py` → seed manifest → `demo_documents_seed.py` → `document_repo.create_with_job`. Validator rule **C11**: must be a date or null, and must be after `effective_date`/`document_date` when present.
- **Excel `outstanding_debt('today')` stays a frozen snapshot, not a live calculation** — a real interpolation engine is a larger, separate feature (not built now, V0 minimalism). Instead, the generator now stamps every workbook with a `Ledger_DemoToday` named range (the same day already written to the hidden `_meta` sheet); `outstanding_debt` compares it against `temporal.today(settings)` (threaded through `run_function(..., today=...)`, injected as a trusted `_today` key never read from the LLM's plan) and refuses (`FunctionError` → the existing "no data" answer) instead of silently serving a stale figure once the two disagree.
- **"What's today's date?" is not a document question** — Balbal Anayasası Ç-7's five data states (Kesin Veri/Veri Yok/Yeterli Veri Bulunmamaktadır/Çelişkili Veri/AI Yorumu) classify *document* answers; a system fact never enters that pipeline. Decision (Naci, 05.10.2026): frontend-only — `CurrentUserResponse`/`CurrentUser.today`/`demo_mode_enabled` ride along on every `/api/auth/login`\|`/me` call, AI-BalBal shows a small top-bar badge; no backend keyword short-circuit was added, so Balbal itself still answers "insufficient data" to this question, unchanged.
- **Shared with the future B-01 agenda:** `temporal.py` is its own module (not folded into `version_chain.py`) precisely so "N days until expiration" is written once and reused when `/api/me/agenda` is built, instead of being redone.
- **Not here:** the ledger scenario for which demo document actually expires (`DOC-ANK-OPS-009`'s `expiration_date`) — candidate dates listed for Naci, no value written without his approval (§ below); live interpolated Excel calculation; a backend-side system-fact answer path.
- **Correction (05.10.2026, found during ADR-027's rollback rehearsal):** the documented switch `DEMO_MODE` was not actually read — pydantic-settings derives the env name from the field (`DEMO_MODE_ENABLED`), so `DEMO_MODE=false` silently kept the default. `Settings` now declares `validation_alias=AliasChoices("DEMO_MODE", "DEMO_MODE_ENABLED")` (same for `ASSIST_MODE`), with a regression test that sets the documented names. Demo behaviour was unaffected (the default is the demo calendar); only the rollback switch was dead.

## ADR-027 — Assist mode: "veri yok" is a no-fabrication rule, not a no-help rule (Tansu Not 2)

**Status:** accepted, behind a flag (default off) · **Phase:** cross-cutting round (05.10.2026) · plan `docs/plans/DAVRANIS_MANTALITESI_PLAN.md` · branch `feat/davranis-mantalitesi`, tag `pre-assist-mode` on the last pre-flag commit
- **Problem (Tansu Not 2, Ç-7.1):** a question the sources cannot answer ended the conversation with one fixed sentence — nothing about what *was* found, which word did not match, or what to ask instead. Ç-7.1's four steps (understanding check → data-state label → "elimde şunlar var, göstereyim mi" → open ending) were never implemented.
- **The fixed sentence stays the verdict (ADR-014).** On a no-answer the `answer` field is still exactly `NO_ANSWER_TEXT`, `answered=false`, `warnings[].kind` unchanged (Ç-7's five states are not extended). Help lives in an **additive** `AskResponse.assist` block: `kind` (`clarify` | `term_mismatch`), `question`, `unmatched_terms`, `candidate_terms`, `available[]`. `null` whenever `ASSIST_MODE` is off (today's default, byte-identical) and on every answered reply.
- **Help ≠ opinion.** Everything in `assist` except one sentence is written by code (`services/assist.py`): which question terms matched no allowed chunk (one LIMIT-1 FTS probe each), which glossary document-side terms do occur in the user's allowed documents, which allowed documents the question touched (`search_metadata` on the zero-chunk path; the retrieved documents, best page each, on the insufficient path — Ç-7.1 step 3 from `retrieved_document_ids`, never from the model's text). These are existence facts about the user's own corpus, not interpretation (rule 6).
- **One bounded model sentence.** With the flag on, rule 11 lets the model append `SORU: <one question>` after the fixed sentence. Code splits it off and keeps it only if it is one sentence ending in `?`, ≤ 200 chars, with no digit/date/currency/percent and no title of a document outside the user's allowed set; otherwise it is dropped (reason logged and stored) and a fixed template is shown. On an answered reply the line is discarded. Worst case is today's behaviour, never a chattier fabrication.
- **ADR-021 holds:** the zero-chunk path still calls no LLM; its assist is lookups inside `allowed_document_ids` only (`search_fts(allowed_ids=…)`, `search_metadata(session, allowed, …)`). ADR-004 is the only gate: a metadata match on a hidden document is not a suggestion (tested).
- **Rule 8 tightened in the flagged prompt** (`SYSTEM_PROMPT_ASSIST`, rules 1–7/9–10 byte-identical): the code-computed `Süre:` line must be copied verbatim (TARIH_SAAT_REPORT §9 observed a paraphrase). If the R2 measurement still shows paraphrase, the fallback is a code-owned `computed_notes` field — not built yet.
- **Audit (rule 4):** `audit_log.assist JSONB` (migration 0015) stores what the user saw, plus `dropped_reason` when a model question was refused.
- **Eval:** safety invariants replace any fixed-sentence expectation — **G1** no number/date in a DOCUMENT answer that is absent from the cited pages' text (+ their headers, BUGÜN, the question; spellings normalised: `10 Ocak 2025` = `10.01.2025` = `2025-01-10`, `44.100.000` = `44,100,000`), and none at all in `assist.question`; **G2** answered → citations, not answered → the fixed sentence first; **G3** nothing in `assist.available` outside what `ask_as_user` may see, nothing from another project when `expected_project` is set, `forbidden_sources` applied to suggestions too. G1–G3 are a 100% gate over every question (`EvalReport.ok`), independent of category thresholds. New categories `ambiguous` / `term_mismatch` (≥ 80%) with `expect_assist`; examples live in `questions.json` v5, never in the prompt.
- **Not here (deferred):** partial answers (`EKSİK:`), waiting for Tansu's Not 8; Not 7 (document still processing) explicitly out of scope; any backend-side system-fact short-circuit (ADR-026 decision stands); the AI-BalBal rendering of `assist` (separate PR).
- **ADR-014 concretization:** "fixed strings" means the *verdict* is fixed; a code-generated statement of what exists and what is missing, and a validated clarifying question, do not contradict it. **ADR-021 concretization:** "no retrieved chunk → no LLM" is unchanged; the assist block on that path is pure code.
